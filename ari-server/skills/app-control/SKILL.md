# 앱 제어 (App Control)

## 원칙

ARI(PM)는 다른 앱의 **내부 프로토콜을 알지 못하며, 알 필요도 없습니다.** 앱별 구체 동작은 각 앱이 자기 세션 안에서 스스로 다룹니다. ARI 에게 허용된 행동은 오직 세 가지입니다:

1. **시작 (준비)** — 대상 앱을 켜서 대화할 수 있는 상태로 만든다.
2. **종료** — 대상 앱을 끈다.
3. **지시 (대화)** — 자연어로 일을 맡긴다.

모든 제어는 통합 툴 `control_app` 하나로 이루어집니다. 호출 방식만 달라집니다.

## 사용 지침

1. **앱 탐색**: 대상 앱 ID를 모르거나 연결 상태가 불확실할 때만 `list_apps` 호출.

2. **지시 (대화) — `message` 모드**: 다른 앱에 일을 맡길 때는 **반드시** `control_app(app, { message: "..." })` 형태로 호출합니다.
   - 사용자 요청을 자연어 그대로, 필요하면 살짝 정돈해서 전달하세요.
   - 커맨드 이름·파라미터를 쓰지 마세요. ARI 가 그 앱의 내부를 아는 것은 원칙 위반입니다.
   - 응답은 자연어 텍스트로 돌아옵니다. 사용자에게 자연스럽게 전하세요.

3. **시작 (준비)**: `message` 모드 호출이 자동으로 앱을 실행하고 연결을 기다립니다. 따라서 "시작"만을 위한 별도 호출은 거의 필요 없습니다. 단순 기동이 필요하면 가벼운 인사나 상태 질문을 `message` 로 보내세요.

4. **종료 — `command` 모드**: `control_app(app, { command: "SHUTDOWN" })`. 이미 꺼진 앱에 보내도 안전 (no-op).

5. **`command` 모드의 역할 제한**: ARI 가 `command` 를 직접 지정하는 경우는 **라이프사이클(`SHUTDOWN`) 하나뿐**입니다. 그 외 모든 도메인 작업은 `message` 모드로 위임하세요.

6. **상태 확인**: 앱의 현재 상태가 필요하면 `message` 로 물어봅니다. 저수준 상태가 꼭 필요할 때만 `read_app_state` 를 씁니다.

7. **주의 사항**: 앱이 응답하지 않거나 타임아웃 시 사용자에게 보고 후 재시도 확인. 프리즈된 앱을 이 스킬로 죽일 수는 없습니다.

8. **응답 작성**: 사용자 응답을 자연어로 설명합니다. 내부 프로토콜 표현을 그대로 노출하지 마세요.
